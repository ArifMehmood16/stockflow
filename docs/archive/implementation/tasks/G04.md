# G04 — Switch ownership atomically and recover migration

PLAN mapping: 6.3. Status lives only in [STATE](../STATE.md).
Prerequisite: G03.

## Read only what this task needs

Read the common workflow in [CURSOR](../../../CURSOR.md), then relevant sections of: G03 verification; epoch registry and routing caches; migration supervisor. Inspect existing collaborators/tests before edits. Paths for future features are proposed locations, not claims that files already exist.

## Deliver

Atomically advance ownership epoch, update/refresh routers and resume writes on one new owner. Fence stale owners and persist cutover progress. Retain old copies for investigation, but define post-cutover rollback as a new verified reverse migration or forward repair after writes resume; an old snapshot is not safely writable again.

## First evidence or failing behavior

Controller/router crash at every cutover boundary leaves exactly one accepted writer; stale router cannot write old owner. A post-cutover write survives repair/reverse migration. Repeated shard addition preserves all rows and idempotency effects.

## Acceptance criteria

Routes animate only after actual accepted ownership switch. Retire old copies only after explicit retention/verification conditions. Migration success conserves quantities, active reservations and request outcomes.

## Verification

make test-sharding-integration; fault-at-transition tests and a two-to-three shard real migration with a small fixture. Use the exact current target names; add a target only where this card introduces it. Record the command and observed result. Never count unavailable infrastructure as a pass.

## Handoff evidence

Epoch history, single-writer evidence and before/after checksums/ledger.

## Keep out of scope

No dual writes, instant rollback to stale data or deletion of the source before verified completion.
