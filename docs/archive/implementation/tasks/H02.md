# H02 — Prove schema-compatible rollback

PLAN mapping: 7.2. Status lives only in [STATE](../STATE.md).

## Read only what this task needs

Read the common workflow in [CURSOR](../../../CURSOR.md), then relevant sections of: H01 deployment; versioned migrations and release contracts. Inspect existing collaborators/tests before edits. Paths for future features are proposed locations, not claims that files already exist.

## Deliver

Implement one concrete expand/backfill/compatible-read-write/contract exercise. Verify both deployed versions during expand, track backfill completion and explicitly gate destructive contract. Disable old-version rollback once compatibility is no longer proven. Use owned run schemas.

## First evidence or failing behavior

Old and new versions operate correctly before contract; bad green can roll back without duplicate writes; an incompatible old version is rejected after contract. Interrupted backfill is safely resumable.

## Acceptance criteria

Guide explains app rollback versus data rollback, mixed-version writes and why destructive changes need a separate reviewed step. No destructive migration runs by default.

## Verification

make test-deployment-integration; two-version SQL/HTTP compatibility tests and rollback drill. Use the exact current target names; add a target only where this card introduces it. Record the command and observed result. Never count unavailable infrastructure as a pass.

## Handoff evidence

Compatibility matrix with evidence for each state and explicit rollback boundary.

## Keep out of scope

No drop/rename migration against the retained global catalog or silent data-loss rollback.
