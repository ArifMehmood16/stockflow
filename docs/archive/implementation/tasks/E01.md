# E01 — Introduce Redis cache-aside safely

PLAN mapping: 4.1. Status lives only in [STATE](../STATE.md).
Prerequisite: D05 and accepted V4.

## Read only what this task needs

Read the common workflow in [CURSOR](../../../CURSOR.md), then relevant sections of: Approved Redis distribution/version/licence decision; Java lifecycle; stock read policy; runtime capability registry. Inspect existing collaborators/tests before edits. Paths for future features are proposed locations, not claims that files already exist.

## Deliver

Add one owned Redis instance and a bounded client/pool with explicit maxmemory/eviction policy. Cache only eligible stock displays; reserve/release/strict reads use the primary. Namespace every key by run, tenant, warehouse/item and schema version. Add corresponding Java simulation events and map build/readiness/cache routing.

## First evidence or failing behavior

Same SKU across tenants/runs cannot share a value. Redis unavailable never permits oversell. Building cache has no effect before readiness. Malformed/oversized entries are rejected safely.

## Acceptance criteria

Make uses documented native Redis prerequisites; Docker has isolated Redis storage/networking. Hit/miss/origin counters and TTL/source/version are visible. New dependencies and distribution licensing are recorded before use.

## Verification

Introduce make test-cache-integration; Redis protocol/namespace tests on owned instances; stock invariants; simulation and frontend tests for new capability. Use the exact current target names; add a target only where this card introduces it. Record the command and observed result. Never count unavailable infrastructure as a pass.

## Handoff evidence

Cache-aside sequence, actual hit/miss proof and memory limit.

## Keep out of scope

No cache as stock authority, unbounded connection pool or automatic Redis install with elevated privileges.
