# E05 — Demonstrate hot keys without promising magic scaling

PLAN mapping: 4.3. Status lives only in [STATE](../STATE.md).
Prerequisite: E04.

## Read only what this task needs

Read the common workflow in [CURSOR](../../../CURSOR.md), then relevant sections of: Cache workload distribution; E01/E03; component inspector and simulation. Inspect existing collaborators/tests before edits. Paths for future features are proposed locations, not claims that files already exist.

## Deliver

Provide a skewed read-hot-key workload. Implement the chosen bounded read-only L1/coalesced-refresh mitigation with explicit version, TTL, size and invalidation semantics, or another justified strategy. Show per-key/cache-instance concentration and the difference between hot reads and serialized hot writes.

## First evidence or failing behavior

One key still concentrates on one Redis owner despite adding unrelated capacity; L1 memory stays bounded; invalidation/expiry and negative-to-positive transitions obey the documented freshness policy.

## Acceptance criteria

Before/after evidence explains latency/origin load and any added staleness. Inspector shows workload skew. The fix cannot alter reservation authority or claim to split a hot row.

## Verification

make test-cache-integration; cache/L1 memory and stale tests; matched hot-read/hot-write experiments; simulator/UI tests. Use the exact current target names; add a target only where this card introduces it. Record the command and observed result. Never count unavailable infrastructure as a pass.

## Handoff evidence

Hot-key share, cache/DB demand, staleness/version observations and remaining bottleneck.

## Keep out of scope

No pretending that more shards automatically distribute a single tenant/key.
