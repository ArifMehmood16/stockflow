# I01 — Restore a backup and prove recovered data

PLAN mapping: 8.1. Status lives only in [STATE](../STATE.md).
Prerequisite: H03 and accepted V8.

## Read only what this task needs

Read the common workflow in [CURSOR](../../../CURSOR.md), then relevant sections of: Owned DB supervisor; inventory ledger; dataset provenance; recovery contracts. Inspect existing collaborators/tests before edits. Paths for future features are proposed locations, not claims that files already exist.

## Deliver

Implement backup of a stopped or consistently snapshotted owned fixture, manifest/checksum and restore into a new owned database. Validate restored schema/rows/reservation ledger before routing. Inject data damage only into a disposable run copy, show that a replica can propagate the same damage and distinguish backup age from observed lost writes.

## First evidence or failing behavior

Wrong ownership/manifest/checksum rejects restore; partial restore never becomes ready; corrupted or missing committed records fail verification. The source and user's postgres database are untouched.

## Acceptance criteria

Expose backup/restore progress, chosen recovery point and measured recovery duration. Native Make uses documented PostgreSQL tools invoked from Java; Docker has equivalent isolated steps.

## Verification

Introduce make test-recovery-integration; backup/restore/mismatch/interruption tests; guided recovery E2E. Use the exact current target names; add a target only where this card introduces it. Record the command and observed result. Never count unavailable infrastructure as a pass.

## Handoff evidence

Restore manifest, known-write reconciliation and source/destination identity proof.

## Keep out of scope

No restoring over the shared database or labelling process startup as successful data recovery.
